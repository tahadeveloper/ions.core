# Two-factor authentication (TOTP)

`Ions\Auth\TwoFactor` provides RFC 6238 time-based one-time passwords (TOTP) —
the codes generated by Google Authenticator, 1Password, Authy and compatible
apps. It is **dependency-free**: base32 (RFC 4648) and HMAC-based code derivation
are implemented in the framework and validated against the official RFC 6238
Appendix B test vectors (SHA1/SHA256/SHA512).

The framework provides the **verifier and helpers**; the **host owns
persistence** (which columns, how they are encrypted) and the **login gate**
(when to challenge). This keeps the user model un-prescribed.

See also: [auth.md](auth.md) (JWT login flow), [security.md](security.md)
(`Encrypter` for encrypting the secret at rest).

## At a glance

```php
use Ions\Auth\TwoFactor;

// 1. Enrolment — generate a secret and show a QR.
$secret = TwoFactor::generateSecret();            // base32, e.g. "JBSWY3DP…"
$uri    = TwoFactor::otpauthUri($secret, $user->email, 'Acme Inc');
// Render $uri as a QR with your own QR library (host-side, see below).

// 2. Confirm — the user scans, types the current code, you verify.
if (TwoFactor::verify($secret, $request->input('code'))) {
    // store the (encrypted) secret + set two_factor_confirmed_at
}

// 3. Recovery codes — show once, store hashed.
$codes  = TwoFactor::generateRecoveryCodes();     // ['abcd-2xkq', …]
$hashed = array_map([TwoFactor::class, 'hashRecoveryCode'], $codes);
```

## API

| Method | Purpose |
| --- | --- |
| `generateSecret(int $bytes = 20): string` | Cryptographically random secret as uppercase base32 (no padding). 20 bytes = 160 bits, the recommended size. |
| `code(string $secret, ?int $ts = null, int $period = 30, int $digits = 6, string $algo = 'sha1'): string` | The TOTP value at a moment in time (for display/testing). |
| `verify(string $secret, string $code, int $window = 1, ?int $ts = null, …): bool` | Timing-safe verify, accepting ±`$window` steps of clock drift. |
| `otpauthUri(string $secret, string $label, string $issuer, …): string` | The `otpauth://totp/…` provisioning URI for authenticator apps. |
| `generateRecoveryCodes(int $count = 8, int $bytes = 10): array` | High-entropy single-use codes, formatted `xxxx-xxxx`. |
| `hashRecoveryCode(string $code): string` | SHA-256 digest for storage. |
| `verifyRecoveryCode(string $code, array $hashedCodes): int\|false` | Matching index (for single-use consumption) or false. |
| `base32Encode` / `base32Decode` | RFC 4648 helpers (exposed for tooling/tests). |

### Drift window

`verify()` accepts the current step plus `$window` steps either side, covering
clock skew between the server and the user's device. The default `window = 1`
(±30 s with the default 30 s period) is the common choice. Verification is
**timing-safe**: every candidate step is compared with `hash_equals()` and the
results are OR-folded, so the method never short-circuits and never leaks which
step matched. Malformed input (wrong length / non-numeric) is rejected before
the secret is touched.

### Algorithm and digits

Defaults are SHA-1, 6 digits, 30 s — what authenticator apps assume when the
provisioning URI omits the parameters. `code()`, `verify()` and `otpauthUri()`
all accept `sha256`/`sha512`, 8 digits, and a custom period if you need them;
keep the same values across enrolment, the URI, and verification.

## otpauth URI → QR (host-side)

`otpauthUri()` emits the standard string; the framework deliberately does **not**
bundle a QR encoder. Render it with whatever your stack already uses:

```php
// Example with endroid/qr-code (host dependency):
$uri = TwoFactor::otpauthUri($secret, $user->email, config('app.name'));
$qr  = (new Endroid\QrCode\Builder\Builder())->data($uri)->build();
return response($qr->getString(), 200, ['Content-Type' => $qr->getMimeType()]);
```

The URI looks like:

```
otpauth://totp/Acme%20Inc:alice%40example.com?secret=JBSWY3DP…&issuer=Acme%20Inc&algorithm=SHA1&digits=6&period=30
```

Both the label and issuer are URL-encoded.

## Recovery codes (single-use)

Recovery codes let a user in when they lose their device. They are
high-entropy random tokens, so a **fast SHA-256 digest is sufficient** for
storage (no slow password hash needed) — `verifyRecoveryCode()` compares every
stored hash with `hash_equals()` so matching is timing-safe.

`verifyRecoveryCode()` returns the **index** of the matching hash; the host is
responsible for **consuming** (removing) it so each code works exactly once:

```php
$stored = $user->two_factor_recovery_codes; // decrypted array of hashes
$index  = TwoFactor::verifyRecoveryCode($request->input('recovery_code'), $stored);

if ($index !== false) {
    unset($stored[$index]);                 // single-use: burn it
    $user->two_factor_recovery_codes = array_values($stored);
    $user->save();
    // …complete the login…
}
```

## Replay protection (optional)

RFC 6238 §5.2 recommends rejecting a code that has already been accepted inside
its validity window. `Ions\Auth\TwoFactorReplayStore` wraps `verify()` and
records the consumed time-step per user in the cache, so the same code cannot be
replayed while the window is still open. `TwoFactor` itself stays pure/stateless
(and trivially testable); reach for the store only when you want replay
protection.

```php
use Ions\Auth\TwoFactorReplayStore;

$store = new TwoFactorReplayStore(app('cache.store'));

if ($store->verifyOnce($user->id, $secret, $request->input('code'))) {
    // valid AND not previously used for this step → proceed
}
```

`verifyOnce()` returns `false` both for a wrong code and for a correct code whose
step was already consumed. A wrong code never burns a step.

## Storing the secret (encrypt at rest)

Treat `two_factor_secret` (and the recovery-code hashes) as sensitive. Encrypt
them with [`Ions\Security\Encrypter`](security.md) before persisting:

```php
$enc = Ions\Security\Encrypter::fromAppKey(env('APP_KEY'));

$user->two_factor_secret = $enc->encrypt($secret);
$user->two_factor_recovery_codes = $enc->encrypt(json_encode($hashed));
$user->save();

// On verify:
$secret = $enc->decrypt($user->two_factor_secret);
```

### Migration stub

A migration stub for the host columns ships at
`src/Auth/stubs/two_factor_columns.stub`. Copy it into your host
`src/Database` (or `app/Database`) and adjust the table name. It adds:

- `two_factor_secret` — encrypted base32 secret (text)
- `two_factor_recovery_codes` — encrypted JSON array of recovery-code hashes (text)
- `two_factor_confirmed_at` — timestamp set once enrolment is confirmed (nullable)

## Login flow: the challenge-after-password pattern

2FA is a **second factor**: verify the password first, then — *before issuing a
JWT* — require a valid TOTP (or recovery) code. The framework's
[`AuthController`](auth.md) issues tokens once credentials check out; to add a
2FA gate, do the TOTP check in your own login action (or a subclass) between the
credential check and `Jwt::issue()`.

```php
// Host login action (sketch).
public function login(Request $request): JsonResponse
{
    $input = (array) RequestInput::parse($request);
    $user  = $this->users->retrieveByCredentials($input);

    if ($user === null || !$this->users->validateCredentials($user, $input)) {
        return Json::error('Invalid credentials', 401);
    }

    // Second factor required?
    if ($user->two_factor_confirmed_at !== null) {
        $code = (string) ($input['two_factor_code'] ?? '');

        if ($code === '') {
            // Tell the client to collect the code (no token yet).
            return Json::error('Two-factor code required', 422, ['two_factor' => true]);
        }

        $enc    = Encrypter::fromAppKey(env('APP_KEY'));
        $secret = $enc->decrypt($user->two_factor_secret);
        $store  = new TwoFactorReplayStore(app('cache.store'));

        $ok = $store->verifyOnce($user->id, $secret, $code)
            || $this->consumeRecoveryCode($user, $code, $enc);

        if (!$ok) {
            return Json::error('Invalid two-factor code', 401);
        }
    }

    // Password + second factor passed → now issue the token pair.
    return Json::ok($this->jwt->issuePair((string) $user->getAuthIdentifier()));
}
```

This is a documented building-block pattern, not a prescribed controller — wire
it to whatever shape your user model and client flow need.
