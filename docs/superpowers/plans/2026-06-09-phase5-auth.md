# Phase 5 — Auth Subsystem Rebuild (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Decouple authentication from Cartalyst Sentinel behind a pluggable `UserProvider`, make `AuthMiddleware` resolve and attach the real authenticated user (not just an id string), harden the JWT (configurable clock leeway, refresh tokens, `jti` revocation), add login rate-limiting, and finally wire the already-built `CsrfMiddleware` into the web pipeline. **This phase resolves D-S(11)** — the Sentinel-for-Illuminate-11 question that gates Phase 4.6 — by making the auth backend swappable (Sentinel adapter for BC; a native Eloquent provider as the L11 escape hatch).

**Architecture:** A new `Ions\Auth` contract layer — `Authenticatable` (a user) + `UserProvider` (`retrieveById`, `retrieveByCredentials`, `validateCredentials`) — sits between the framework and any backend. Two implementations: `SentinelUserProvider` (wraps the existing `Guard`/Sentinel, preserving today's behavior) and `EloquentUserProvider` (native, no Sentinel — the L11 path). `AuthProvider` binds the configured provider as `auth` (container id `user_provider`). `AuthMiddleware` becomes: Bearer → `Jwt::verify` → `UserProvider::retrieveById($claims->userId)` → attach the **user object** to the request (not just the id). JWT gains a leeway param + refresh/revocation via a cache-backed `jti` deny-list. `CsrfMiddleware` joins the web middleware stack. The static `Guard` facade stays as a deprecated BC shim delegating to the provider.

**Tech Stack:** unchanged — PHP 8.2+, Illuminate 10 (cache for the revocation deny-list + rate limiter), `lcobucci/jwt` 5 (+ `lcobucci/clock` for leeway), Cartalyst Sentinel 7 (now behind an adapter), Symfony security-csrf 6.4, Pest 2 + PHPStan 2 + CS-Fixer. No new runtime deps expected (uses `illuminate/cache` — already required).

**Branch:** fresh branch off `main` (e.g. `phase5-auth`). `main` holds Phases 0–3 + Phase 4 (minus the 11-jump). **145 tests green.**

## Decision D-A — default auth backend (surface before 5.2)
The framework is wired to Sentinel today (`Guard`, `Auth/Sentinel/User`, `Auth/Sentinel/config.php`). Phase 5 introduces a `UserProvider` abstraction with TWO adapters. The decision: **which is the default**, and **does Sentinel stay**?
- **Option A (RECOMMENDED, lowest disruption): keep `SentinelUserProvider` as the default** (existing apps unchanged), AND ship `EloquentUserProvider` as a config-selectable alternative + the L11 escape hatch. Revisit at Phase 4.6: if Cartalyst Sentinel has no Illuminate-11 release, switch the default (or the framework's own auth) to the native Eloquent provider then — by which point the abstraction makes it a config change, not a rewrite.
- **Option B: drop Sentinel now**, make `EloquentUserProvider` the only/default backend. Bigger break (Sentinel's activation/throttle/reminder features must be reimplemented or dropped), but removes a heavy, less-maintained dependency immediately and fully unblocks L11.

**This plan is written for Option A** (abstraction + both adapters, Sentinel default). **RESOLVED (user, 2026-06-09): Option A** — keep `SentinelUserProvider` as the default and ship `EloquentUserProvider` as the config-selectable native alternative + L11 escape hatch. Note: this directly determines D-S(11) in the Phase 4 plan — once this lands, 4.6 can proceed because auth is no longer hard-bound to Sentinel.

## Current-state facts (verified against `main`)
- `src/Http/Middleware/AuthMiddleware.php`: `__construct(?Jwt $jwt)`; `handle()` parses the `Bearer` header, `Jwt::verify()`, sets `$request->attributes->set('auth_user_id', $claims->userId)`, then `$next`. **It attaches only the id STRING — it does NOT resolve a user object or consult any UserProvider.** Returns a 401 `JsonResponse` on missing/invalid/expired token or null Jwt.
- `src/Security/Jwt.php`: `issue(string $userId, array $claims=[])` / `verify(): Claims`. Uses `StrictValidAt` with **no leeway** and `nbf=iat=now` (D5-A: NTP-skew risk). No refresh, no revocation/`jti` deny-list (the `jti` is set but never checked).
- `src/Providers/AuthProvider.php`: binds `jwt` only (via `Kernel::buildJwt()`). **No `auth`/`user_provider` binding** (deferred here).
- `src/Http/Middleware/CsrfMiddleware.php`: fully built + tested (injectable `CsrfTokenManagerInterface`, protects POST/PUT/PATCH/DELETE, 419 on mismatch) but **NOT in `Kernel::defaultMiddleware()`** — the web stack is `[TrustedHost, SecurityHeaders, Cors]` (no CSRF). So CSRF is not actually enforced yet.
- `src/Auth/Guard/Guard.php`: a static class wrapping Sentinel facades (`check`/`login`/`logout`/`forgetCode`/`checkResetCode`/`completeReset`), with `Guard::constructStatic()` invoked at file-load to bootstrap Sentinel. `GuardUser`/`GuardRole`/`GuardControl` similarly wrap Sentinel. `src/Auth/Sentinel/User.php` extends `Cartalyst\Sentinel\Users\EloquentUser`; `config.php` maps Sentinel classes.
- `Kernel::buildJwt()` builds the `Jwt` from `env('APP_KEY')`/`env('APP_NAME')`/`config('app.jwt.ttl')`.
- **D5-C (issuer/audience rejection tests) is already DONE** (Task 1.1 follow-up added them to `JwtTest`). D5-A (clock leeway) and D5-B (user-bound / validate userId, don't trust `['success']`) remain — addressed in 5.3/5.4.
- The Sentinel auth layer (`Guard*`) has **zero test coverage** today — closing that gap is a Phase 5 deliverable.

## Sub-phase 5.1 — Auth contracts (Authenticatable + UserProvider)

### Task 5.1.1: Define the contracts
**Files:** `src/Auth/Contracts/Authenticatable.php`, `src/Auth/Contracts/UserProvider.php`, tests.

- [ ] **Step 1: Failing tests** — a fake `UserProvider` returning a fake `Authenticatable` satisfies the contracts:
```php
<?php
use Ions\Auth\Contracts\Authenticatable;
use Ions\Auth\Contracts\UserProvider;

test('a UserProvider returns an Authenticatable by id', function () {
    $provider = new class implements UserProvider {
        public function retrieveById(string|int $id): ?Authenticatable {
            return $id === '42' ? new class implements Authenticatable {
                public function getAuthIdentifier(): string|int { return '42'; }
                public function getAuthIdentifierName(): string { return 'id'; }
            } : null;
        }
        public function retrieveByCredentials(array $credentials): ?Authenticatable { return null; }
        public function validateCredentials(Authenticatable $user, array $credentials): bool { return false; }
    };
    expect($provider->retrieveById('42')?->getAuthIdentifier())->toBe('42')
        ->and($provider->retrieveById('999'))->toBeNull();
});
```

- [ ] **Step 2: Implement** the two interfaces:
```php
<?php
// src/Auth/Contracts/Authenticatable.php
namespace Ions\Auth\Contracts;

interface Authenticatable
{
    public function getAuthIdentifier(): string|int;
    public function getAuthIdentifierName(): string;
}
```
```php
<?php
// src/Auth/Contracts/UserProvider.php
namespace Ions\Auth\Contracts;

interface UserProvider
{
    public function retrieveById(string|int $id): ?Authenticatable;
    /** @param array<string,mixed> $credentials */
    public function retrieveByCredentials(array $credentials): ?Authenticatable;
    /** @param array<string,mixed> $credentials */
    public function validateCredentials(Authenticatable $user, array $credentials): bool;
}
```

- [ ] **Step 3: run + commit** `feat(auth): Authenticatable + UserProvider contracts`.

## Sub-phase 5.3 — AuthMiddleware resolves the user (D5-B)

### Task 5.3.1: resolve + attach the user, not just the id
**Files:** `src/Http/Middleware/AuthMiddleware.php`, `Kernel::defaultMiddleware()`, tests.

- [ ] `AuthMiddleware` constructor gains the `UserProvider`: `__construct(?Jwt $jwt, ?UserProvider $users = null)`. After `Jwt::verify()` yields `$claims`, call `$user = $this->users?->retrieveById($claims->userId)`. If a provider is configured and the user is NOT found (deleted/revoked) → **401** (don't trust a token whose subject no longer exists — this is the concrete D5-B fix: validate the user, not just the token). Attach BOTH: `$request->attributes->set('auth_user_id', $claims->userId)` (BC) and `$request->attributes->set('auth_user', $user)` (the resolved `Authenticatable`). If no provider is bound (back-comp / id-only mode), keep today's id-only attach.
- [ ] `Kernel::defaultMiddleware()` api stack: construct `new AuthMiddleware(jwt, user_provider)` resolving `user_provider` from the container when bound (fallback null → id-only).
- [ ] Tests (extend `AuthMiddlewareTest`): valid token + known user → 200 + `auth_user` is the Authenticatable; valid token + unknown/deleted user → 401; no-provider mode → 200 + id-only attach (BC). `ApiController::authUserId()` keeps working; optionally add `authUser(): ?Authenticatable`.
- [ ] Commit `feat(auth): AuthMiddleware resolves the user via UserProvider; reject tokens for unknown users (D5-B)`.

## Sub-phase 5.4 — JWT hardening: clock leeway (D5-A), refresh, revocation

### Task 5.4a: configurable clock leeway (D5-A) — fully specified
**Files:** `src/Security/Jwt.php`, `Kernel::buildJwt()`, `tests/Unit/Security/JwtTest.php`.

- [ ] Add a constructor param `int $clockLeewaySeconds = 0` to `Jwt`; pass it to `StrictValidAt` as a `DateInterval`: `new StrictValidAt($clock, new \DateInterval("PT{$this->clockLeewaySeconds}S"))` (guard 0 → no interval / `PT0S`). `Kernel::buildJwt()` reads `config('app.jwt.leeway', 0)`. Test: a token whose `iat`/`nbf` is a few seconds in the future (simulating issuer-ahead skew) is REJECTED with leeway 0 but ACCEPTED with leeway ≥ the skew. Default 0 preserves current behavior.
- [ ] Commit `feat(jwt): configurable clock-skew leeway (D5-A)`.

### Task 5.4b: refresh tokens + jti revocation (cache deny-list)
**Files:** `src/Security/Jwt.php` (or a new `TokenService`), a cache-backed `RevocationStore`, tests.

- [ ] Add token **revocation**: a `jti` deny-list stored in `illuminate/cache` (already a dep). `Jwt::verify()` (or a wrapping `TokenService`) checks the parsed `jti` against the deny-list and throws `TokenException` if revoked. A `revoke(string $token|Claims): void` adds the `jti` (with TTL = remaining token lifetime). `logout` → revoke the current token.
- [ ] Add **refresh tokens**: issue a longer-lived refresh token (separate audience/claim, e.g. `typ=refresh`); a `refresh(string $refreshToken): string` verifies the refresh token (not revoked) and issues a new access token; rotating the refresh token + revoking the old `jti`. Decide storage (stateless refresh with rotation + deny-list, or a `refresh_tokens` table) — spec in the expansion; recommend stateless + jti rotation to avoid a new table.
- [ ] Tests: revoked token → 401; refresh issues a valid new access token; a refresh token can't be used as an access token (audience/typ check). Commit `feat(jwt): refresh tokens + jti revocation deny-list`.

## Risks & mitigations
- **Sentinel testability needs its DB schema.** Mitigate (5.2.1): add the Sentinel tables to the test fixture (in-memory SQLite) — this both enables the adapter test AND closes the long-standing untested-Sentinel gap. If wiring Sentinel's schema into the fixture is heavy, fall back to a mocked-facade unit test for the adapter and note the limitation.
- **CSRF wiring can break existing web flows.** Mitigate (5.6): audit fixture web routes (current state-changing ones are none/GET); make it config-toggleable; document the break loudly.
- **Refresh/revocation scope creep.** Mitigate: prefer stateless refresh + `jti` rotation over a new table; keep the deny-list in the existing cache. If it balloons, split 5.4b into its own plan.
- **D-A indecision.** Default to Option A (Sentinel adapter + native provider both shipped); the abstraction means the L11 default-switch is a config change, not a rewrite.
- **`lcobucci/clock` for leeway** — already a dep (Phase 1.1). Confirm `StrictValidAt` accepts the `DateInterval` leeway in the installed v5.
